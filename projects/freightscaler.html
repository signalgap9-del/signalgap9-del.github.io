The product

Which route exposes cargo to the least risk? FreightScaler compares route alternatives not just by travel time but by live weather risk, official NWS alerts, and road-event exposure — with per-segment explanations (rain, flood, wind, heat, winter), saved route watchlists with monitoring thresholds, and a multi-tenant SaaS account layer. If a data source is unavailable, the UI says so rather than showing fabricated data.

Architecture evolution

The platform grew through four phases, each triggered by a user demand that broke a different scaling axis:

PhaseTriggerWhat brokeResponse
Route risk queryInitial product—Lambda + DynamoDB, fully serverless
Fleet telemetryLive truck tracking~28M GPS events/day, WebSocket fan-outKafka + TimescaleDB hypertable + nginx LB
Freight marketplaceCarrier matching500 concurrent bidsCQRS + optimistic locking + Redis Sorted Set
SettlementDelay liabilityMulti-step paymentsSaga orchestrator + atomic wallet + idempotency

Telemetry is write-heavy, tracking is connection-heavy, bidding is contention-heavy, settlement is consistency-heavy — different axes a monolith can't scale independently.

Backend decisions

  • Serverless-first, hybrid where it earns it — Lambda+DynamoDB for request/response; dedicated compute only where connection counts demand it
  • DynamoDB operational store + PostGIS hybrid for geospatial queries
  • Async OR-Tools VRP off the request path; an ML delay model gated behind 4 fail-closed promotion checks before it could affect solver costs
  • Dual-ledger quota + idempotency keys on every mutation; plan entitlements (FREE/PRO/TEAM/INTERNAL) enforced server-side
  • NL route planning via an OptiMUS-style multi-agent pattern — LLM constraint extraction → solver formulation → explanation, with schema-repair loop and model fallback

Frontend & operations

React/TypeScript client renders segment-level risk breakdowns so users see why a corridor scores differently. A /status page exposes live data-source health, retry/fallback counters, and performance snapshots — operational transparency as a product feature. Terraform-managed infra, GitHub Actions CI with security scanning, promote-to-prod and rollback pipelines.

Honest gaps

Billing isn't wired (the entitlement boundary exists so payment slots in later); the marketplace phase is documented more than deployed; settlement is design + foundation, not a live money path. The boundaries landed before the risky parts did — deliberately.
