The production AI open-source stack worth adopting

Yunseop Im · Software engineer, AI engineering · M.S. CS, Georgia Tech

Every week a new "AI framework" launches and most of them solve a problem you don't have yet. After building and operating LLM systems in production, here's the shorter list — the open-source tools I actually reach for, what each one is genuinely good at, and where the marketing outruns the reality.

Serving: SGLang (and vLLM)

If you self-host models, SGLang is the serving engine worth knowing. Its edge over naive serving is structured generation — guided decoding that constrains output to a schema or grammar during inference, not after. That matters more than it sounds: cited answers, JSON-only responses, and tool-call formatting all become reliable instead of "usually parses." Continuous batching and KV-cache management are the other half — throughput on a single GPU improves dramatically versus naive sequential decoding.

vLLM is the other serious option — PagedAttention made it the default for a reason. Reach for SGLang when you need constrained/structured output and agentic workloads; reach for vLLM when ecosystem breadth matters more.

Observability: Langfuse

"The agent works in the demo" dies in production without traces. Langfuse is the open-source LLM observability layer — traces every LLM call, tool invocation, and retrieval step, with latency/cost/token breakdowns per request. Self-hostable, OpenTelemetry-compatible. If you're running agents or RAG in production and can't answer "why did that response take 8 seconds and cost $0.04," you need this before you need a better model.

Agents: LangGraph vs. raw tool-calling

LangGraph earns its complexity when your agent has cycles — planning, retry, human-in-the-loop, state that must survive restarts. For linear prompt→tools→answer flows, raw tool-calling with a thin orchestration loop is simpler and cheaper. The mistake is adopting LangGraph for a demo-shaped problem and inheriting its state-machine complexity forever.

Tool protocol: MCP

The Model Context Protocol is becoming the USB-C of agent tooling — a standard way to expose tools, data sources, and prompts to any MCP-compatible client. Building an MCP server for your internal APIs turns "agent can't reach our system" into an afternoon of work instead of a custom integration per agent. It's young; the spec still moves — but the direction is clear and the tooling is real.

Retrieval: Qdrant / pgvector / hybrid

Vector DB choice is mostly solved: Qdrant or pgvector cover most needs. The part that isn't solved is retrieval quality — dense embeddings alone miss exact identifiers (part numbers, error codes, names). Production RAG almost always wants hybrid: sparse (BM25) + dense, fused, then reranked. I wrote a zero-dependency study of this plus graph expansion in graphrag-lab.

Evaluation: Ragas

Ragas gives you metrics for RAG without hand-labeling everything — faithfulness, answer relevance, context precision/recall as computable scores. Pair it with a golden dataset and you have regression tests for retrieval quality, which is the difference between "the RAG feels better" and "the RAG measurably improved."

Routing: LiteLLM

LiteLLM normalizes the OpenAI API surface across providers — one client, dozens of backends, automatic fallbacks and cost tracking. When your product needs "use Gemini for video, OpenAI for agents, Claude for writing" — or when a provider has an outage — this is the boring infrastructure that saves you.

The honest summary

Serving: SGLang/vLLM · Tracing: Langfuse · Agents: LangGraph (only if cyclic) · Tools: MCP · Retrieval: hybrid + rerank · Evals: Ragas + golden sets · Routing: LiteLLM

None of these are magic. The leverage is in combining them with real evals and honest failure handling — which is why the unglamorous parts (tenant isolation, quotas, verification layers) matter more than which framework you picked.
