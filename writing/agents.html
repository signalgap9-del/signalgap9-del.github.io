Running autonomous AI agents safely in a real repo

Yunseop Im · Georgia Tech MSCS · AI agents / LLM systems

I run AI agents daily on a production multi-tenant SaaS. The hard part was never "can the agent write code" — it's trusting it not to break things while nobody's watching. This post is about the harness I built for that: devin-harness.

The problem: agents fail silently, not loudly

Most agent failures aren't crashes. They're gray failures: a deploy that "succeeded" while a queue stopped draining, an edit that passed review but never ran a test, a session that quietly edited a secret file. A diff review catches none of these because the damage isn't in the diff — it's in what the agent didn't do.

What the harness actually does

  • Exec guard — a pre-tool hook that blocks dangerous shell commands deterministically (regex, <50ms, no model call). Cheap enough to run on every call.
  • File guard — same idea for edits: blocks secret files, migration edits, and runtime-state changes before they happen.
  • Session ledger — every tool call appended to action-log.jsonl (secrets redacted), so a reviewer can audit the whole session, not just the final diff.
  • Claim guard — if files changed but no test ran afterward, the session ends with a loud "unverified" advisory instead of a green checkmark.
  • Typed review gates — deterministic secret/suppression scan → npm supply-chain audit → a typed LLM judgment over the diff with persistent state, so resolved findings never re-block.

Why this matters beyond one repo

The pattern generalizes: guardrails at the tool-call boundary > prompts asking the agent to be careful. A rule the agent can't bypass beats a rule it might ignore. Everything in the repo is MIT-licensed and drop-in: node setup.mjs /path/to/your/repo.
