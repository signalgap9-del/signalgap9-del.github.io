Running LLM inference on customer GPUs — what on-prem serving actually takes

Yunseop Im · Software engineer, AI engineering · M.S. CS, Georgia Tech · 2026

"Just call the API" works until it doesn't. For enterprise customers with engineering drawings, supplier contracts, and unreleased product data, sending prompts to a third-party LLM endpoint is a non-starter — the data legally can't leave the building. That constraint turns "add an AI feature" into an infrastructure problem: you now own the GPU, the serving stack, and the failure modes.

This is a field guide to what that actually involves, from running production inference on customer-owned hardware. The stack: SGLang serving Gemma-class models, continuous batching, KV-cache tuning, and guided decoding for structured output. The lessons are mostly about constraints, not benchmarks.

Constraint 1: you don't choose the hardware

Cloud inference assumes you pick the GPU. On-prem, the customer already bought it — maybe last year, maybe a mixed fleet, maybe whatever was cheapest. Your serving stack has to degrade gracefully across SKUs you didn't select: different memory ceilings, different interconnects, different thermal envelopes. The first design question isn't "what's the fastest config" — it's "what's the slowest GPU we have to support, and does the model even fit?"

Practical consequence: quantization isn't optional, it's the baseline. A model that fits comfortably on an A100 may not fit on the customer's RTX card at all, and the fallback path has to be decided before launch, not during the first OOM at 2am customer time.

Constraint 2: serving is a systems problem, not a model problem

SGLang (and vLLM) earn their complexity here. The features that matter in production aren't the headline ones:

  • Continuous batching — requests arrive unpredictably; without batching, GPU utilization collapses and latency variance explodes. This is the difference between "works in a notebook" and "works for 40 concurrent users."
  • KV-cache management — the cache is where memory pressure actually lives. Tuning eviction and allocation policy is most of the serving work; the model weights are the easy part.
  • Guided decoding — constraining output to a schema or grammar during inference, not after. For citation-grounded answers — every response must reference the document it came from — this is what makes structured output reliable instead of "usually parses."

The counterintuitive part: most of the engineering effort goes into the unsexy layer — request queuing, timeout behavior, graceful degradation when the GPU is saturated — not into model selection.

Constraint 3: quality is a regression problem

A cloud model gets updated silently; your on-prem model is frozen at whatever version you deployed. That means quality isn't a one-time evaluation — it's a regression surface. The working setup we use:

  • Golden-set regression tests — a fixed set of real queries with expected citation behavior, run on every config change. If guided decoding parameters shift, the tests catch it before users do.
  • Faithfulness checks — answers are scored against their retrieved sources, not just for fluency. A confident wrong answer with a fake citation is worse than no answer.
  • Human handoff — below a confidence threshold, the system escalates instead of guessing. In engineering domains where a wrong answer about a part revision can cause a real-world error, "I don't know" is a feature.

Constraint 4: operations you didn't sign up for

On-prem serving means you inherit the customer's operational reality:

  • Observability is yours — no provider dashboard. You need your own metrics for queue depth, time-to-first-token, cache hit rates, and error rates, plus alerting that pages someone who can actually fix it.
  • Updates are deliberate — model upgrades, driver updates, and serving-stack updates all require regression runs. "Just redeploy" is a change-management process.
  • The network is hostile — customer firewalls, proxies, and air-gapped segments are the norm, not the exception. Telemetry that assumes outbound internet access silently fails.

The honest summary

On-prem LLM serving isn't "deploy a model." It's operating a production inference service under hardware constraints you didn't choose, quality regressions you have to test for, and an operational surface you fully own. The teams that succeed treat it like infrastructure — with the same rigor as the databases and queues around it.

The leverage isn't in picking the right model — it's in the boring layers: serving configuration, structured output guarantees, regression testing, and knowing when to say "I don't know." Those are the parts that decide whether on-prem AI is a product or a demo.
